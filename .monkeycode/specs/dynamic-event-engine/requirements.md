# 动态事件引擎需求文档

## 概述

动态事件引擎（Dynamic Event Engine）是一个旨在解决游戏事件重复性问题，并提供个性化、无限事件体验的系统。通过结合"预置种子库 + 云端 AI 生成 + IndexedDB 动态存储 + 混合推荐算法"，实现用户游玩过程中事件的持续丰富和个性化匹配。

## 业务需求

### BR-1: 解决事件重复问题
**用户痛点**：当前游戏在长时间游玩后，用户会反复遇到相同的事件，降低游戏新鲜感和沉浸感。

**成功标准**：
- 用户在连续游玩 2 小时以上时，事件重复率低于 20%
- 同一 family 的事件在 7 天内不会重复出现

### BR-2: 个性化事件体验
**用户痛点**：所有用户遇到相同的事件序列，缺乏"针对感"和"懂我"的体验。

**成功标准**：
- 根据用户行为画像（偏好打工、偏好修仙、经常违约等）动态调整事件触发权重
- 画像匹配度高的事件触发概率提升 50% 以上

### BR-3: 无限事件扩展
**用户痛点**：事件总数有限（当前约 50 个），无法支撑长期游玩的内容消耗。

**成功标准**：
- 预置种子库包含 200+ 个高质量事件
- 游玩过程中可通过 AI 持续生成新事件并注入游戏
- IndexedDB 动态池支持存储 1000+ 个事件

## 功能需求

### FR-1: 双层事件池架构

#### FR-1.1: 静态基础池
- **描述**：保留现有的 `events.json` 作为基础事件池
- **职责**：提供核心规则事件（催收、还款、基础行动反馈）
- **加载时机**：游戏启动时同步加载

#### FR-1.2: 动态生成池
- **描述**：基于 IndexedDB 的事件存储层
- **职责**：存储 AI 生成的个性化事件
- **容量目标**：支持 1000+ 事件（约 5-10MB）
- **持久化**：跨会话保留，不清除浏览器数据不丢失

#### FR-1.3: 预置种子库
- **描述**：打包在 `public/seed-events.json` 中的高质量事件集
- **内容要求**：
  - 200+ 个事件，覆盖所有 event family
  - 符合"赛博朋克修仙"世界观
  - 参考真实新闻、社会事件、小说情节进行改编
  - 数值平衡经过校验
- **加载策略**：首次访问时从 IndexedDB 检查是否已导入，未导入则从种子库导入

### FR-2: 云端 AI 事件生成

#### FR-2.1: Vercel Edge Function API
- **端点**：`/api/generate-events`
- **功能**：接收游戏状态上下文，调用 AI API 生成事件 JSON
- **AI 模型**：使用免费/低成本 API（如 Groq + Qwen2.5）
- **输出格式**：符合 `EventDefinition` 类型的事件数组（5-10 个/次）

#### FR-2.2: 静默触发机制
- **触发条件**（满足任一即可）：
  - 玩家游玩时间超过 30 分钟
  - 动态池事件数低于 50 个
  - 检测到事件重复率超过阈值（>30%）
- **执行策略**：使用 `requestIdleCallback` 在浏览器空闲时发起请求
- **用户体验**：生成过程完全后台进行，不阻塞当前游玩

#### FR-2.3: 上下文提取
- **提取内容**：
  - 用户行为画像（偏好、习惯）
  - 当前游戏状态（压力、债务、分班）
  - 近期事件历史（避免重复）
- **Prompt 构建**：基于上下文生成个性化 Prompt

### FR-3: 混合推荐算法

#### FR-3.1: 行为画像权重调整
- **画像维度**：
  - 财务风险等级（low/medium/high/extreme）
  - 教育信用等级
  - 制度顺从等级
  - 身体资产等级
  - 行为标签（打工党、修仙党、违约惯犯等）
- **权重计算**：画像匹配度高的事件权重 × 1.5，不匹配的 × 0.7

#### FR-3.2: 全局去重机制
- **冷却策略**：
  - 同 ID 事件：cooldownDays（已有逻辑）
  - 同 family 事件：7 天内互斥（已有逻辑）
  - 全局多样性：最近 7 天出现过的事件类型，权重降低 50%
- **历史记录**：维护最近 14 天的事件触发记录

#### FR-3.3: 事件选择管线
```
1. 合并静态池 + 动态池候选事件
2. 应用触发条件过滤（trigger 匹配）
3. 应用冷却过滤（cooldown + familyHistory）
4. 应用画像权重调整
5. 应用全局去重降权
6. 加权随机选择
```

### FR-4: 事件校验与安全

#### FR-4.1: Schema 验证
- **验证时机**：AI 生成事件入库前、种子库导入时
- **验证规则**：
  - 必须符合 `EventDefinition` 类型
  - 所有字段类型正确
  - effects 的 target 必须在对应状态对象中存在
  - delta 值在合理范围内（避免数值爆炸）

#### FR-4.2: 数值平衡约束
- **约束规则**：
  - cash 相关 delta：不超过当前现金的 50% 或 5000 灵石
  - stat 相关 delta：单次不超过 ±20
  - debt 相关 delta：不超过总债务的 30%
- **超范围处理**：自动截断到合理范围并记录警告日志

## 非功能需求

### NFR-1: 性能
- 事件选择管线执行时间 < 10ms
- IndexedDB 读写操作不阻塞主线程
- 种子库加载时间 < 500ms

### NFR-2: 存储
- IndexedDB 容量上限：50MB（防止无限膨胀）
- 达到上限时采用 LRU 策略淘汰最旧事件

### NFR-3: 兼容性
- 向后兼容现有存档格式
- 不破坏现有事件触发逻辑
- 降级策略：AI 生成失败时，系统退化为仅使用静态池 + 种子库

### NFR-4: 离线可用
- 种子库和静态池支持离线游玩
- AI 生成仅作为增强功能，失败不影响核心游戏体验

## 约束条件

### C-1: 技术约束
- 必须使用 Nuxt 3 + Vue 3 技术栈
- IndexedDB 操作必须封装为 composable
- Edge Function 必须符合 Vercel 部署规范

### C-2: 内容约束
- 种子库事件必须符合游戏世界观（赛博朋克修仙、债务压迫）
- 不得生成违背伦理道德的内容
- 事件文案风格需与现有事件保持一致（压抑、讽刺、现实主义）

### C-3: 成本约束
- AI API 调用成本需控制在免费额度内
- 单次生成请求不超过 10 个事件
- 生成频率限制：每 30 分钟最多 1 次

## 验收标准

1. [ ] 种子库成功导入 IndexedDB，事件数量 ≥ 200
2. [ ] 双层事件池合并选择逻辑正常工作
3. [ ] 混合推荐算法生效，画像匹配事件触发率提升 ≥ 50%
4. [ ] 全局去重机制生效，7 天内同 family 事件不重复
5. [ ] Edge Function API 可正常调用并返回有效事件 JSON
6. [ ] Schema 验证拦截无效事件，错误事件不入库
7. [ ] 降级策略生效，AI 生成失败时游戏不崩溃
8. [ ] 全量测试通过（530+ 测试用例）
